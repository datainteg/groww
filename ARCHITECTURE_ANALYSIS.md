# Architecture Analysis — Groww AI Trading System

## Executive Summary

This is a single-broker (Groww) AI options-scalping system for Indian index F&O (NIFTY/BANKNIFTY/SENSEX/FINNIFTY): a Flask REST backend + APScheduler workers, MongoDB + Redis, and a React/Zustand polling frontend. It is capable of placing real-money orders (EXECUTION_MODE switchable to LIVE per user).

The single most important fact: the system as committed is NOT safe to run against a live account today. Real broker credentials are checked into the repository — a Groww API SECRET and a live-scope access token (backend/groww/GrowwAPI.py, backend/groww/env), plus a live Redis Cloud password and Telegram bot token (backend/.env) — and there is no .gitignore anywhere in the repo. The encryption key that protects all stored broker credentials defaults to a hardcoded constant. These must be rotated immediately, before any further work.

Against the user's stated priorities, two structural defects dominate. (1) ACCURACY/RESULTS: the auto-trading core is effectively inert and the signals it would produce are statistically unsound. The confidence gate has a units mismatch — strategies store min_confidence as a percent (e.g. 70) while the engine compares against a 0-1 fraction (verified at trading_engine.py:162 vs decision_engine.py:128) — so API-created strategies never fire. Even when they do, "confidence" is a weighted sum that is not a probability, is inflated by volatility regardless of direction (decision_engine.py:127), double-counts correlated indicators, and is computed on still-forming candles over mis-bucketed timeframes (a UTC-vs-IST double-fault). (2) REAL-TIME: under any production WSGI server the scheduler never starts (app.py:133-138 is __main__-only and commented "Optional"), so candle sync, direction, auto-entries, and SL/target monitoring all silently do nothing — open live positions would be unmanaged. All market data is REST-polled (no streaming), analysis runs on incomplete bars, and direction is cached as a Python repr string that other workers cannot read.

The codebase shows real engineering care (graceful Redis degradation, empty-data sync guard, numpy-aware JSON, an atomic kill switch), but the trading-critical paths are broken in ways that would either prevent trading entirely or trade on wrong/stale data. Recommended sequence: (A) emergency credential rotation + secret hygiene, (B) make the engine actually run and actually gate correctly, (C) fix the timezone/closed-candle data foundation, (D) overhaul signal fusion for calibrated, regime-aware, cost-aware signals, (E) harden live-order safety (fail-closed locks, input validation, LIVE step-up).

## Architecture Overview

Three tiers. Frontend: React 18 + Zustand, JWT in localStorage, Axios interceptor, HTTP polling only (3-30s; no WebSocket/SSE), client-side indicator math for charts. Backend: Flask app (app.py) wiring six blueprints (auth/market/strategy/trade/settings/instruments) behind flask-jwt-extended, a CustomJSONProvider for numpy/datetime, and CORS. Persistence: MongoDB (users, settings, strategies, trades, candles, instruments) + Redis (LTP cache 10s TTL, direction cache, trade locks via SETNX).

Real-time/compute is driven by background workers, not requests. SchedulerService (scheduler.py, APScheduler, BackgroundScheduler timezone Asia/Kolkata): market_heartbeat_job every 5s fetches LTP for the three indices via GrowwClient REST, caches to Redis, then calls TradingEngine.evaluate_strategies + monitor_active_trades; sync_and_aggregate_job every 60s does a full 7-day historical candle fetch and delete+insert into MongoDB, then TimeframeAggregator builds 5m/15m/30m/60m/1D; instrument_sync at 08:00 IST (delete_many+insert_many); reconcile_orders_job every minute (calls a no-op stub). DirectionScheduler recomputes market direction every 1s from MongoDB candles. CRITICAL: scheduler_service.start() is only invoked under app.py's __main__ block (and labeled optional), so under gunicorn/uwsgi none of this runs.

Signal path: candles -> TimeframeAggregator (label/closed='left', IST conversion in one place but naive local time in candle_service) -> DecisionEngine (weighted fusion of patterns/momentum/volatility/S-R/volume into a 0-1 "confidence", 0.70 threshold) and MarketDirectionEngine (1m/5m/15m weighted 20/25/35, +VWAP/volume bonuses). Trade path: routes acquire a Redis lock (fail-open), resolve ATM strike from instruments, call engine.execute_entry/exit through PaperBroker or GrowwClient; trades recorded in MongoDB. GrowwClient loads an encrypted token from Mongo per instantiation with no refresh loop; candle_service uses its own separate raw requests path. There is dual source-of-truth for execution_mode (users vs settings collections) and three near-identical trading_engine files (engine, _fixed, _backup).

# Per-Subsystem Deep-Read

## API & Entry Layer — Flask app wiring, blueprints, JWT auth, request validation, error handling, market/strategy/trade/settings/instruments routes

**Purpose:** This subsystem is the HTTP gateway for the AI options-trading system running against Groww broker. It exposes a REST API consumed by the frontend, wires six Flask blueprints (auth, market, strategy, trade, settings, instruments), enforces JWT-based authentication, proxies live market data from Groww or Redis cache, drives trade execution through paper and live brokers, and maintains user settings, strategy lifecycle, and instrument metadata in MongoDB. All trading decisions and order placements flow through this layer.

**Data flow:** Request arrives at Flask (app.py:42) → CORS preflight handled (app.py:60-70) → after_request re-stamps CORS headers (app.py:72-79) → JWT decoded by flask_jwt_extended → blueprint route handler invoked → handler reads user/strategy from db (database/mongodb.py singleton) → optionally reads LTP from redis_client (database/redis_client.py singleton) → calls service layer (GrowwClient, PaperBroker, TradingEngine, CandleService, InstrumentSync) → serialises response through CustomJSONProvider (app.py:15-37) → response returned. Key service calls by route: auth_routes → db.create_user / db.get_user_by_email / GrowwClient.generate_access_token; market_routes → redis_client.get_cached_ltp / GrowwClient.get_quote / GrowwClient.get_ltp / candle_service.get_candles / analyze_direction; strategy_routes → db.get/create/update_strategy / candle_service.get_candles_for_analysis / analyze_market / get_trading_engine; trade_routes → acquire_trade_lock (Redis SETNX) / get_paper_broker / get_groww_client / engine.execute_entry / engine.execute_exit / db.create_trade; settings_routes → db.get_settings / db.upsert_settings / update_user_field / TelegramAlert; instruments_routes → instrument_sync.sync_instruments / db.instruments.aggregate.

**Real-time aspects:** LTP is cached in Redis with a 10-second TTL (redis_client.py:47-49). The /api/market/ltp/{symbol} route reads Redis first, falls back to a live Groww API call, and stores the result back with 10 s TTL (market_routes.py:271-290). Indices summary is cached 2 seconds (market_routes.py:252). Market direction is computed by DirectionScheduler running every 1 second in a daemon thread (direction_scheduler.py:37). Candle data is stored in MongoDB and refreshed by a scheduler service; routes read from MongoDB, not the live Groww stream. The /api/market/direction/{symbol} endpoint with force_refresh=false returns whatever the scheduler last computed; with force_refresh=true it re-fetches from MongoDB candles and re-analyzes. There is no WebSocket or server-sent events layer; all real-time data reaches the frontend by frontend polling. The candle_service._get_smart_window uses local system time (datetime.now(), not IST-aware) for computing fetch windows. The direction calculation for /api/market/direction endpoint falls back to using 5 min candles copied as 1 min candles (df_1m = df_5m.copy()) when real 1 min data is absent, which degrades direction accuracy silently.

## Real-time Data & Scheduling

**Purpose:** This subsystem is responsible for fetching live market prices (LTP/OHLC/quotes) from the Groww REST API via polling, storing historical and real-time candle data in MongoDB, aggregating 1-minute candles into 5m/15m/30m/60m/1D timeframes, caching live prices in Redis for the trading engine, running instrument master sync, and firing Telegram alerts. It is the sole source of real-time accuracy for all downstream signal generation, strategy evaluation, and trade execution decisions.

**Data flow:** 1. market_heartbeat_job (scheduler.py:123) fires every 5s -> GrowwClient.get_ltp (groww_client.py:294) REST GET /v1/live-data/ltp for ['NSE_NIFTY','NSE_BANKNIFTY','BSE_SENSEX'] -> on success, price written to RedisClient.cache_ltp (redis_client.py:47) with 10s TTL, then TradingEngine.evaluate_strategies and monitor_active_trades called with that price. 2. sync_and_aggregate_job (scheduler.py:174) fires every minute via CronTrigger -> CandleService.sync_candles (candle_service.py:166) -> _execute_sync -> fetch_candles_from_groww (candle_service.py:33) REST GET /v1/historical/candle/range with 7-day lookback -> results written via _save_to_db (delete+insert) or _upsert_to_db -> TimeframeAggregator.aggregate_all (timeframe_aggregator.py:101) on in-memory 1m DataFrame -> db.upsert_candles (mongodb.py:76) bulk_write for 5m/15m/30m/60m/1D. 3. DirectionScheduler._run_loop (direction_scheduler.py:64) fires every 1s -> reads 1m candles from MongoDB (candle_service.get_candles) -> re-aggregates to 5m/15m in-memory -> analyze_direction -> result written to direction_cache dict and Redis key 'direction:{symbol}' with 10s TTL. 4. instrument_sync_job (scheduler.py:290) at 08:00 IST -> GrowwClient.download_instruments (groww_client.py:684) HTTP GET CSV -> filter -> db.instruments.delete_many+insert_many. 5. Token path: GrowwClient._load_token (groww_client.py:50) reads encrypted token from MongoDB on every new client instantiation; no automatic refresh loop exists anywhere.

**Real-time aspects:** All market data is fetched exclusively via REST polling - there is no WebSocket or streaming feed. LTP is polled every 5 seconds via get_ltp (scheduler.py:54-60). Candles are fetched via historical REST endpoint every 60 seconds (scheduler.py:65-71) with a 7-day lookback window on every call. Direction is recomputed every 1 second (direction_scheduler.py:37) but reads stale MongoDB candles written at most 60 seconds ago - not fresh tick data. Redis TTLs: LTP 10s (redis_client.py:47), direction result 10s (direction_scheduler.py:139). The system has no WebSocket feed, no tick accumulation, no live-candle formation from real ticks, and no sub-second market data. The last candle in the 1-minute series from the broker is typically the current forming (incomplete) candle, and no logic distinguishes or discards it before feeding it to signal analysis.

## Groww Trading Platform - Authentication, Secrets Management & Order Execution

**Purpose:** This subsystem handles user authentication (JWT), encrypted storage of Groww broker API credentials, and routing of trade orders to either a paper broker or the live Groww API. Because EXECUTION_MODE can be set to LIVE, a successful compromise of credentials or the order-placement path can result in real-money orders being placed on a user's brokerage account. The audit covered secrets hygiene, cryptographic key handling, JWT configuration, broker-credential storage, and authorization on order/mode-switching endpoints.

**Data flow:** Credentials flow: client POSTs email/password (+optional Groww api_key/api_secret) to /api/auth/register or /api/auth/login (auth_routes.py:34, 102). Passwords are hashed via werkzeug generate_password_hash (line 60). Groww api_key/api_secret are encrypted via Encryption.encrypt (encryption.py:20) using a Fernet key derived from config.ENCRYPTION_KEY (encryption.py:15-18) and stored in MongoDB (mongodb.py:141). /api/auth/update-groww-credentials (auth_routes.py:241) re-encrypts keys and immediately calls GrowwClient.generate_access_token (groww_client.py:195) which builds a SHA-256 checksum from the api_secret (checksum.py:8-27), retrieves a live broker access token, encrypts it (auth_routes.py:275) and stores it. Order flow: client sends JWT (axios.ts:13-18 reads token from localStorage) to /api/trade/place-order, /quick-trade, /execute-strategy (trade_routes.py:89, 523, 464). ## Groww Decision / Market-Direction Signal Engine

**Purpose:** Two parallel signal engines drive options entries on NIFTY/BANKNIFTY/SENSEX. DecisionEngine (decision_engine.py) fuses ~67 indicators across 5 buckets (patterns, momentum, volatility, S/R, volume) into a BULLISH/BEARISH signal with a weighted confidence, gated at 0.70, and is consumed by trading_engine.evaluate_strategies() to fire CE/PE entries. MarketDirectionEngine (market_direction_engine.py) is a lighter multi-timeframe (15m/5m/1m + volume + VWAP) UP/DOWN/NEUTRAL + strength engine run every 1s by direction_scheduler for the live dashboard. timeframe_aggregator.py resamples 1m candles into higher TFs feeding the direction engine.

**Data flow:** 5m candles (last 500) are pulled from MongoDB in trading_engine.evaluate_strategies (lines 134-145), wrapped in a DataFrame and passed to decision_engine.analyze (decision_engine.py:68). analyze() calls detect_all_patterns / calculate_all_momentum / calculate_all_volatility / calculate_all_support_resistance, derives per-bucket (score, direction), then combines them at lines 95-128 into bullish_score/bearish_score plus a volatility_factor add-on (line 127), thresholded at 0.70 (line 130). The result's signal+confidence is read back at trading_engine.py:147-148 and compared against strategy.min_confidence (default 0.6, line 162) to fire execute_entry. Separately, direction_scheduler._update_direction (direction_scheduler.py:83) loads 200x 1m candles, aggregates to 5m/15m via timeframe_aggregator.aggregate, injects live LTP from Redis, and calls analyze_direction → _calculate_final_signal (market_direction_engine.py:526) producing weighted_score with hard 60/40 cutoffs (lines 560-565), cached to Redis with 10s TTL.

**Real-time aspects:** DecisionEngine runs on a 5s strategy heartbeat against DB-stored 5m candles; it does NOT use live LTP, so signals are stale up to one 5m bar plus DB-sync lag. MarketDirectionEngine runs at 1Hz and overrides only current_price/current_volume with live LTP (market_direction_engine.py:179-180) while all EMAs/RSI/structure are computed on closed aggregated candles. The aggregator's resample uses label='left', closed='left' (timeframe_aggregator.py:80), so the most recent bucket is the still-forming bar — meaning the last 5m/15m candle repaints every second as new 1m data arrives, and indicators computed on .iloc[-1] flip intra-bar. Redis direction cache has a 10s TTL but the loop is 1s, so staleness is bounded; however the 1m DB candles themselves depend on sync_realtime cadence which is not guaranteed sub-minute.

## Indicators & Patterns (backend/analysis: momentum, volatility, support_resistance, patterns)

**Purpose:** This subsystem computes 67 technical signals over NIFTY F&O 5-minute candles: 17 momentum indicators, 13 volatility indicators, 13 support/resistance indicators, and 24 chart/candlestick/harmonic patterns. Each emits a BULLISH/BEARISH/NEUTRAL signal plus a 0-1 strength/confidence, and patterns also emit entry/target/stop_loss prices. The DecisionEngine aggregates them into a single weighted signal used to enter scalping trades every 5 seconds. The user's goals are accuracy, real-time correctness, and best results.

**Data flow:** Live path: trading_engine.evaluate_strategies() runs every ~5s -> candle_service.get_candles(symbol,'5',500) returns oldest-first list -> pd.DataFrame(candles) with datetime index -> analyze_market(df) -> DecisionEngine.analyze (decision_engine.py:68). analyze() calls detect_all_patterns(df) (patterns/__init__.py:5 -> detect_all_primary/candlestick/harmonic), calculate_all_momentum (momentum/indicators.py:270), calculate_all_volatility (volatility/indicators.py:353), calculate_all_support_resistance (support_resistance/indicators.py:302). Every indicator reads df['close'/'high'/'low'/'volume'].values and almost universally takes the LAST element via .iloc[-1] / [-1] / rolling(...).iloc[-1]. Results flow back to _analyze_patterns (decision_engine.py:182), _analyze_momentum (197), _analyze_volatility (221), _analyze_support_resistance (235), _analyze_volume (258), then a weighted bullish/bearish score (95-128) produces the final signal at >=0.70 confidence. CRITICAL: the aggregation layer reads keys that the indicator/pattern layer never emits (see issues), so large parts of the signal silently collapse to NEUTRAL/0.5. The last candle fed in is the currently-forming 5-min bar (candle_service returns whatever is in db.candles including the live bar), so every [-1]-based read repaints intrabar.

**Real-time aspects:** Polling model: evaluate_strategies polls every 5s and recomputes the entire indicator stack on a 500-bar 5-minute window. There is no streaming/incremental update and no caching of completed-bar values, so the full 67-indicator + 24-pattern stack (including O(n^2) volume profiles and O(n) Python loops in ADX/OBV/MFI/Nadaraya-Watson) is recomputed from scratch every 5 seconds for every index — wasteful and latency-prone, contradicting the sub-1ms HFT target. More dangerously, almost every indicator keys off df.iloc[-1], which on a live feed is the still-forming current 5-min candle. RSI, MACD, Stochastic, Bollinger %B, all candlestick patterns (doji/engulfing/hammer/star), pivots and VWAP therefore REPAINT continuously within the bar: a 'bullish engulfing' or 'close > upper band' that appears at second 30 can vanish by bar close, producing entries on signals that never actually existed at confirmation. VWAP is computed as a cumsum over the entire 500-bar window (not session-anchored / not reset at 09:15 IST), so it drifts and is not the intraday VWAP traders expect. Pivots use the last single candle's H/L/C rather than the prior completed daily/period bar, so they recompute every bar instead of being fixed for the session. There is also no staleness/timestamp check: if the candle feed stalls, the engine keeps trading on the last frame with no guard.

## Decision & Direction Engine (backend/analysis)

**Purpose:** This subsystem turns OHLCV candle data into actionable trading signals for NIFTY/BANKNIFTY/SENSEX F&O scalping. The legacy DecisionEngine fuses ~67 indicators (patterns/momentum/volatility/support-resistance/volume) into a single BULLISH/BEARISH signal with a confidence in [0,1], used by trading_engine to fire CE/PE entries. The newer MarketDirectionEngine produces a UP/DOWN/NEUTRAL direction plus a 0-100 strength from a 5-component weighted blend across 1m/5m/15m timeframes, recomputed every 1 second by the direction_scheduler. The TimeframeAggregator resamples 1m candles to 5m/15m/30m/60m for both engines.

**Data flow:** Two parallel pipelines. (A) Legacy: trading_engine.evaluate_strategies (trading_engine.py:134-148) pulls 5m candles, builds a df, calls analyze_market -> DecisionEngine.analyze (decision_engine.py:68-180). analyze() calls detect_all_patterns, calculate_all_momentum/volatility/support_resistance, then the private _analyze_* scorers (L182-272), combines them into bullish_score/bearish_score with WEIGHTS (L98-124), computes confidence = max(bullish,bearish)+volatility_factor clamped to 1.0 (L127-128), thresholds at 0.70 (L130-133), classifies regime (L136-141), and returns a dict scrubbed by to_python_type (L19-37). (B) Realtime: direction_scheduler._run_loop (direction_scheduler.py:64-73) every 1s during market hours calls _update_direction (L83-139): fetches last 200 1m candles, aggregates via timeframe_aggregator.aggregate (timeframe_aggregator.py:36-99) to 5m/15m, fetches live LTP from Redis, calls analyze_direction -> MarketDirectionEngine.analyze (market_direction_engine.py:158-249). analyze() runs _analyze_15m_trend (L251-310), _analyze_5m_structure (L312-398), _analyze_1m_momentum (L400-465), _analyze_volume (L467-492), _analyze_vwap (L494-524), then _calculate_final_signal (L526-575) blends weighted scores with bonuses and maps to direction/strength. Result cached in-memory and Redis (ex=10). Both engines read iloc[-1] of the latest (still-forming) bar; the direction engine substitutes live_ltp for the forming close.

**Real-time aspects:** MarketDirectionEngine is driven by a 1-second polling loop (direction_scheduler.py:37,64-73) over a Python thread; there is no streaming/event push. Each tick re-aggregates 200 1m candles into 5m/15m on the fly (no incremental update) and blends the live Redis LTP into the forming bar. Results are cached in-process and mirrored to Redis with a 10s TTL (L139). The legacy DecisionEngine is invoked from the slower strategy heartbeat on 5m candles. Staleness/repaint risks are severe: (1) analysis runs on the in-progress candle (the aggregator never drops the open bucket), so EMA/RSI/structure/candle-strength all repaint within the bar; (2) live_volume is not passed by the scheduler (only live_ltp at L130), so volume uses the stale last closed 1m volume vs a 20-bar average that includes that same forming bar, biasing the ratio; (3) Redis LTP freshness/availability is unchecked — a stale or missing LTP silently falls back to the candle close with no age guard; (4) no debounce/hysteresis means the 60/40 direction boundary flips on micro-noise every second.

## Trading Engine & Paper Broker (NIFTY F&O scalping, Groww broker)

**Purpose:** This subsystem drives strategy evaluation, order lifecycle (entry/exit), SL/target/trailing-SL management, position tracking, and P&L computation for both PAPER (simulated) and LIVE (Groww) execution. The scheduler heartbeat calls TradingEngine.evaluate_strategies() and monitor_active_trades() every 5 seconds per index; PaperBroker simulates fills with slippage against Groww live LTP and maintains a virtual cash account in MongoDB.

**Data flow:** Heartbeat: scheduler.market_heartbeat_job() (scheduler.py:123-170) fetches index LTP via groww.get_ltp(['NSE_NIFTY','NSE_BANKNIFTY','BSE_SENSEX'], segment='CASH'), caches it in redis (cache_ltp expiry=10s), then per index calls engine.evaluate_strategies(symbol, price) and engine.monitor_active_trades(symbol, price). ENTRY: evaluate_strategies (trading_engine.py:114-172) reloads settings, queries active strategies, pulls 5m candles via candle_service.get_candles(db,index,'5',500), builds a DataFrame, calls decision_engine.analyze_market -> signal+confidence; if confidence>=min_confidence and no OPEN trade for the strategy, calls execute_entry (282-388). execute_entry resolves the option symbol (resolve_dynamic_symbol 243-276 using redis-cached spot, ATM rounding, regex lookup in db.instruments), places a MARKET BUY through _get_broker().place_order, derives execution_price, computes SL/target via risk_manager.calculate_sl_target (71-100), and persists via db.create_trade (status 'OPEN'). MONITORING: monitor_active_trades (174-237) gets db.get_active_trades, fetches option LTP via _get_option_ltp (77-108 -> paper.get_ltp or groww.get_ltp with NFO_ prefix), evaluates risk_manager.check_exit_condition (207-246) for target/SL, and if triggered calls execute_exit (417-480); otherwise recomputes trailing SL via risk_manager.calculate_trailing_sl (102-135) and persists current_sl. EXIT: execute_exit places MARKET SELL, derives final_exit_price, computes pnl=(exit-entry)*qty, calls db.close_trade (sets status 'CLOSED'), db.update_strategy_pnl. PAPER fills: paper_broker.place_order (142-271) reads LTP via get_ltp (NSE_ prefix), applies _calculate_slippage (118-140), mutates positions list and balance, and writes back through db.upsert_paper_account (twice on SELL).

**Real-time aspects:** Polling, not streaming. The scheduler fires every 5s but only when is_market_open(); index LTP is cached in redis for 10s. Option LTPs for monitoring and for paper fills are fetched on-demand via REST get_ltp per call (no batching), so each monitored trade triggers a separate synchronous HTTP request inside the 5s loop — latency stacks and can exceed the 5s interval with multiple open trades, causing skipped/aliased heartbeats. Signals are computed from 5-minute candles synced by a separate aggregation job; for 5s scalping the entry signal can be up to ~5 minutes stale. Paper fills use the same LTP snapshot as the trigger check (no simulated latency between decision and fill), and slippage is random rather than spread/volume-based, so simulated accuracy diverges from live. Exit checks compare LTP to SL/target only at 5s boundaries, so intrabar wicks through SL are not caught and fills are modeled at the post-move LTP, understating realized losses.

## Real-time Data & Scheduling

**Purpose:** This subsystem is responsible for fetching live quotes and historical candles from the Groww REST API, aggregating 1-minute candles into higher timeframes (5m, 15m, 30m, 60m, 1D), caching LTP values in Redis, and driving two concurrent schedulers: a 5-second heartbeat that prices indices and triggers strategy evaluation, and a 1-minute job that full-syncs 1m candles then aggregates all timeframes. A separate 1-second DirectionScheduler reads those DB candles and publishes market-direction signals to Redis for cross-process consumption. All data fetching is pure REST polling; there is no WebSocket/streaming path.

**Data flow:** 1. Every 5 s: scheduler.py:market_heartbeat_job() -> GrowwClient.get_ltp() (groww_client.py:294) -> LTP stored in Redis via redis_client.cache_ltp() (redis_client.py:47, TTL=10 s) -> engine.evaluate_strategies() + engine.monitor_active_trades() called inline.

2. Every 60 s: scheduler.py:sync_and_aggregate_job() -> candle_service.sync_candles(db, symbol, '1', token) (candle_service.py:166) which calls _get_smart_window(1) (candle_service.py:128) to compute start/end, then fetch_candles_from_groww() (candle_service.py:33) via raw requests.get to /v1/historical/candle/range. On success, candles are written to MongoDB 'candles' collection via _save_to_db() (delete+insert) or _upsert_to_db(). Next, candles_1m fetched from DB (candle_service.get_candles limit=50000), converted to DataFrame, passed to timeframe_aggregator.aggregate_all() (timeframe_aggregator.py:101) for 5m/15m/30m/60m, plus manual '1D' resample in scheduler.py:229-248. Each higher-TF result is written to MongoDB via db.upsert_candles() (mongodb.py:76).

3. Every 1 s: direction_scheduler.py:_update_direction() -> candle_service.get_candles(db, symbol, '1', 200) (DB read) -> timeframe_aggregator.aggregate() inline -> redis_client.get_cached_ltp() -> analyze_direction() -> redis_client.set('direction:{symbol}', ..., ex=10).

4. Daily at 08:00: instrument_sync.sync_instruments() -> GrowwClient.download_instruments() (static method, unauthenticated) -> filter FNO, keep 3 expiries -> db.instruments.delete_many({}) + insert_many().

5. Token path: GrowwClient.__init__ -> _load_token() -> db.get_user_by_id() -> encryption.decrypt(stored_token). On every request _get_headers() retries _load_token() only if token is None (line 71-72); no automatic refresh on 401.

**Real-time aspects:** Quotes are fetched via pure REST polling. LTP heartbeat fires every 5 seconds (scheduler.py:55-61) via get_ltp() (a single batch call for all three indices). The Redis TTL for LTP is 10 seconds (redis_client.py:47), meaning a price cached at T=0 may still be read at T=9.9 s while the next heartbeat has not yet completed — worst-case staleness matches the TTL exactly. The DirectionScheduler re-reads that same Redis LTP every 1 second but the underlying price does not update faster than 5 seconds. Candle data in MongoDB is refreshed every 60 seconds by sync_and_aggregate_job; that job always fetches from the Groww historical endpoint (not a live tick feed), so the 'current' candle stored in DB can be up to 60 s stale. There is no WebSocket subscription, no tick aggregation, and no live-candle builder for the forming bar. Higher timeframes (5m, 15m, 60m) are derived entirely from the DB's 1m candles, not from direct API calls, so their staleness is: 60 s (1m sync latency) + aggregation time. The direction:symbol Redis keys have a 10-second TTL (direction_scheduler.py:139), so the direction signal served to the frontend can be up to 10 s behind the last computation.

## Frontend (real-time UI and state)

**Purpose:** React 18 single-page application built with Zustand stores, Axios REST polling, and lightweight-charts. It renders live market data (NIFTY/BANKNIFTY/SENSEX F&O), AI signal decisions, active trade positions, strategy management, and candlestick charts. All real-time updates are achieved exclusively through setInterval polling — there are no WebSockets. The UI serves as the primary control plane for an AI options-scalping engine running on a Python/Flask backend via Groww broker APIs.

**Data flow:** 1. App.tsx (line 31-33): on mount calls useAuthStore.initialize(), which reads localStorage for access_token and user JSON, sets isAuthenticated synchronously — no server validation.

2. Polling chains (all page-level useEffect intervals, no shared manager):
   - Dashboard.tsx line 248-256: fetchAllDirections every 30s; line 259-261: fetchDecision on symbol change (no interval).
   - Signals.tsx line 30-38: fetchDecision every 10s via SIGNAL_POLL_INTERVAL hardcoded as 10000.
   - Trades.tsx line 116-122: fetchActiveTrades + fetchPositions + fetchDailyPnl every 10s.
   - Charts.tsx line 110-114: loadData (candles + fetchDecision + fetchDirection) every 5s via config.MARKET_POLL_INTERVAL.
   - Dashboard has no polling for indices, strategies, engine status, or P&L — only manual refresh or symbol change triggers fetchDecision.

3. API layer: axios.ts wraps all calls with Bearer token from localStorage (line 15). Response interceptor (line 30-52) hard-redirects on 401 via window.location.href. No token refresh logic is wired.

4. Stores: Zustand plain stores (no persist middleware). market.store.ts: fetchExpiries (line 64) reads response.expiries which is always undefined because instrumentsApi.getExpiries already unwraps and returns a plain string[]. trade.store.ts: refresh() (line 192-199) calls fetchActiveTrades, fetchPositions, fetchDailyPnl, fetchLimits in parallel. strategy.store.ts: fetchDecision (line 73-90) stores result under decisions[symbol] map.

5. Pages read from stores and compute derived values locally: Dashboard.tsx line 518-519 computes live P&L client-side from trade.ltp; Trades.tsx lines 72-100 recomputes win-rate and realized P&L from the trades array. Charts.tsx lines 192-206 calls calculateSMA/calculateEMA/calculateBollingerBands from indicators.ts client-side using candle data already returned by the backend.

6. Auth token flow: login response → localStorage → axios interceptor reads on every request. Token expiry is never checked. refreshToken() exists in auth.api.ts (line 43-46) but is never called anywhere in the codebase.

**Real-time aspects:** All real-time data uses interval polling — no WebSocket or SSE connection exists. Polling intervals are: market direction 30s (Dashboard), AI decision on-demand only (Dashboard) / 10s (Signals), active trades 10s (Trades), candles + AI decision + direction 5s (Charts). There is no shared polling manager, so when multiple pages are open simultaneously (or even during normal navigation without cleanup), duplicate concurrent polls fire against the same endpoints. The direction store's isBackground flag (direction.store.ts line 45) is the only attempt to suppress loading spinners during background polls. Candle data staleness risk: Charts page fetches 300 candles every 5s using setData which replaces the entire series — there is no incremental/append update, meaning the chart flickers on each poll. The AI decision on Dashboard has no polling interval at all (only fires when analysisSymbol changes or on manual refresh), so it can display a signal that is 30+ minutes old while the direction engine cards refresh independently every 30s — these two data sources can contradict each other visually. The fetchActiveTrades response does not include a fresh LTP from the broker; the LTP displayed on the active trades table (Dashboard line 518, Trades line 387) uses trade.ltp which is whatever value the backend returned at last poll — it is not a live streaming price.
